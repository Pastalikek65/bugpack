# Supported inputs and limits

Supported evidence: HAR 1.2 JSON, UTF-8 `.log`/`.txt`, still PNG and supported JPEG screenshots. The app is a static browser workbench; portable packages require Node.js 24 and a current Chromium browser. The bundled text CLI shares its engine; images require the browser. Windows 11 x64 and Ubuntu 24.04 x64 are qualification targets. Use each release's `verification.json` for exact tested hosts, browser versions and acceptance results; a source checkout, later documentation commit or green local build does not inherit or extend a release qualification. Files do not get uploaded to a backend. Server scripts listen only on 127.0.0.1 and reject POST; self-hosting the static `web` directory requires a trustworthy origin and security headers.

HAR cleanup creates a fresh projection of supported fields. Authentication/cookies, unapproved headers, unknown extensions and comments are dropped. Bodies are omitted by default; an explicitly applied supported-body policy can retain structurally cleaned JSON/form text. See the [policy and CLI guide](cli.md). The supported response status and timing fields remain useful for debugging, but full HAR information is deliberately not retained. Supported URLs keep their hostname/path and noncredential query fields; inspect these for private values. The summary counts omitted data rather than treating it as reviewed preserved content.

Text cleanup uses fixed credential patterns, including authorization/cookie lines, quoted or unquoted credential assignments, JWT-like values and common signed-URL keys. It cannot classify arbitrary private strings, names or personal values. Edit the clean copy manually. A clean HAR edit must remain valid supported HAR; export sanitizes it again. The Markdown report also receives fixed credential cleanup.

Images are validated before decoding, drawn to a fresh canvas, covered by integer-coordinate opaque masks, and encoded as PNG. PNG ancillary metadata and JPEG source metadata are not retained. Animated PNG is unsupported. Image processing checks dimensions before browser decoding and after orientation; these checks do not make the browser an OS memory sandbox. Removing a mask affects only the local review workspace; the already exported PNG contains no reversible mask layer.

Limits: 16 MiB per original file and per cleaned/edited text, 64 MiB aggregate original inputs, 50 files, 5,000 HAR entries, 200,000 JSON nodes and depth 40. Images are at most 8,192 pixels on a side and 16,000,000 decoded pixels. Regenerated image bytes are subject to the 64 MiB aggregate bundle-input budget; total uncompressed bundle contents are bounded by 128 MiB; the completed ZIP has the same 128 MiB cap. Worker operations have a 60-second deadline and can be cancelled. These are rejection limits, not throughput guarantees or a process-memory ceiling. Malformed or unsupported input fails explicitly and is never archived as its original.

Processing counts include app-reported first-pass redaction/omission facts and any export-pass changes. They describe operations and omissions, not a proof that no secret remains. Source filenames and absolute paths are not included automatically. A user can still write private information into a report or miss a screenshot mask; review all outputs before sharing.

URL cleanup supports bounded userinfo and path/query processing of valid hierarchical `scheme://` URIs (scheme length at most 32). Nested URI recursion and percent decoding are capped; deeper or malformed content fails closed. `mailto` and arbitrary encoded personal strings are outside automatic detection. Shared URL/query work limits can reject an input before another size/count limit is reached; limits describe rejection bounds, not a promise that every input below each individual limit is accepted.

## Format compatibility

Redaction policy files use schema version 1. Default exports use processing-summary version 1; explicitly selected policies use version 2. Unsupported policy versions fail with an explicit error. A processing summary is an output, not an importable policy. The app does not persist its evidence workspace or import ZIPs; replacing the static application does not migrate or modify original files. Previously cleaned HAR/log text can be processed again, but omitted bodies and an old summary's count history cannot be recovered from that text.
